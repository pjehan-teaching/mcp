Le SDK et symfony/mcp-bundle

Le SDK PHP officiel

  • Paquet Composer mcp/sdk, développé par la PHP Foundation et le projet Symfony
  • SDK officiel de niveau 3, en version 0.8 : expérimental jusqu'à la version 1.0
  • Ères legacy et modern servies par le même code
  • Déclaration des tools, resources et prompts par attributs PHP

Le bundle symfony/mcp-bundle (version 0.14) l'intègre à Symfony : route, configuration, conteneur de services, commandes.

Le SDK et le bundle sont expérimentaux : leur API peut encore changer d'une version à l'autre.

Un nouveau projet

On repart d'un projet vide pour mesurer ce que le SDK apporte :

symfony new tickets
cd tickets
composer require orm serializer symfony/mcp-bundle nyholm/psr7 # « n » à la recette Docker
composer require --dev orm-fixtures maker
echo 'DATABASE_URL="sqlite:///%kernel.project_dir%/var/data.db"' > .env.local
php bin/console make:entity Ticket --field=title:string --field=description:text --field=status:string:20 --field='assignee:string?'
  • nyholm/psr7 : le transport HTTP du SDK manipule des requêtes PSR-7 ; sans implémentation, chaque requête échoue en 500
  • Mêmes commandes que pour tickets-raw : .env.local, entité Ticket et TicketRepository
  • Il ne reste qu'à copier src/DataFixtures/AppFixtures.php depuis tickets-raw
  • Créez la base : make:migration, doctrine:migrations:migrate puis doctrine:fixtures:load
  • Les tools renvoient des tableaux : le NormalizerInterface du Serializer y transforme les tickets
Installation

Configurer le serveur

Le bundle n'a pas de recette Flex : config/packages/mcp.yaml n'existe pas après l'installation, il faut le créer. Dans config/routes.yaml, il suffit d'ajouter la route mcp.

# config/packages/mcp.yaml
mcp:
    servers:
        default:
            name: 'tickets'
            version: '1.0.0'
            http:
                path: /mcp
            registry: '*'
# config/routes.yaml
controllers:
    resource: routing.controllers

mcp:
    resource: .
    type: mcp
  • Le bundle enregistre lui-même la route /mcp : plus de contrôleur à écrire
  • registry: '*' expose tous les tools, resources et prompts de l'application
Act as Server

Les tools : TicketTools

<?php

namespace App\Mcp;

use App\Repository\TicketRepository;
use Mcp\Capability\Attribute\McpTool;
use Mcp\Capability\Attribute\Schema;
use Mcp\Exception\ToolCallException;
use Symfony\Component\Serializer\Normalizer\NormalizerInterface;

final class TicketTools
{
    public function __construct(
        private readonly TicketRepository $tickets,
        private readonly NormalizerInterface $normalizer,
    ) {
    }

    /**
     * Liste les tickets de support, éventuellement filtrés par statut.
     */
    #[McpTool(name: 'list_tickets')]
    public function list(#[Schema(type: 'string', enum: ['open', 'closed'])] ?string $status = null): array
    {
        $tickets = $status ? $this->tickets->findBy(['status' => $status]) : $this->tickets->findAll();

        return ['tickets' => $this->normalizer->normalize($tickets)];
    }

    /**
     * Récupère le détail d'un ticket à partir de son identifiant.
     */
    #[McpTool(name: 'get_ticket')]
    public function get(int $id): array
    {
        $ticket = $this->tickets->find($id) ?? throw new ToolCallException("Le ticket #$id n'existe pas.");

        return $this->normalizer->normalize($ticket);
    }
}

Ces 40 lignes remplacent le contrôleur, l'interface, le registre et les deux classes de tools.

Ce que fait le SDK

  • #[McpTool] transforme la méthode en tool ; sans name, son nom est celui de la méthode
  • Le docblock devient la description du tool
  • Les types des paramètres deviennent le inputSchema : int $id donne un entier obligatoire ; #[Schema] ajoute des contraintes
  • Le SDK valide les arguments reçus avant d'appeler la méthode
  • Un tableau renvoyé devient un contenu texte JSON et un structuredContent
  • ToolCallException produit un résultat isError: true ; toute autre exception, une erreur JSON-RPC au message générique

Toute classe de src/ portant un attribut MCP est détectée à la compilation du conteneur : TicketTools reçoit le dépôt et le normalizer par autowiring.

Tester dans les deux ères

On lance le serveur comme avant, puis on déclare deux connexions dans inspector.json :

{
  "mcpServers": {
    "tickets": { "type": "http", "url": "http://localhost:8000/mcp", "protocolEra": "modern" },
    "tickets-legacy": { "type": "http", "url": "http://localhost:8000/mcp" }
  }
}
npx @modelcontextprotocol/inspector --cli --config inspector.json --server tickets \
  --method tools/call --tool-name list_tickets --tool-arg status=closed
npx @modelcontextprotocol/inspector --cli --config inspector.json --server tickets-legacy \
  --method tools/list

La même URL répond aux deux ères : le transport examine chaque requête et choisit l'ère qui y répond.

The Modern Era

Un serveur adapté au flux d'écoute

En ère modern, la liste des tools met 30 secondes à s'afficher dans l'Inspector.

L'Inspector ouvre subscriptions/listen, un flux SSE que le SDK garde ouvert 30 secondes. Deux réglages de PHP sont nécessaires :

  • Pas de tampon de sortie (output_buffering=0) : sinon l'accusé de réception du flux reste dans le tampon et l'Inspector attend sa fin avant de lister les tools
  • Plusieurs processus (PHP_CLI_SERVER_WORKERS) : un serveur à un seul processus ne peut pas répondre à tools/list tant que le flux est ouvert

Remplacez symfony serve par le serveur interne de PHP :

PHP_CLI_SERVER_WORKERS=4 php -S localhost:8000 -t public -d output_buffering=0

Un flux ouvert longtemps demande un serveur qui l'envoie immédiatement et qui reste disponible pour les autres requêtes.

Le résultat produit par le SDK

{
  "content": [{
    "type": "text",
    "text": "{\n    \"tickets\": [\n        {\n            \"id\": 3,\n            \"status\": \"closed\", …"
  }],
  "structuredContent": {
    "tickets": [
      { "id": 3, "status": "closed", "assignee": "bob", "title": "Export CSV vide", "description": "…" }
    ]
  },
  "isError": false,
  "_meta": {
    "io.modelcontextprotocol/serverInfo": { "name": "tickets", "version": "1.0.0" }
  }
}
  • structuredContent : les mêmes données, exploitables par le client sans parser de texte
  • Le schéma généré pour ?string $status = null : {"type": "string", "default": null, "enum": ["open", "closed"]}
  • Sans type: 'string' dans #[Schema], le SDK déduirait "type": ["null", "string"] : légal, mais moins portable, l'Inspector le signale car certains clients (Gemini) n'acceptent qu'un seul type

Exercice

Créez le serveur du fil rouge avec le SDK.

  1. Créez le projet tickets, installez les paquets, créez .env.local et l'entité avec make:entity, puis copiez AppFixtures et créez la base.
  2. Écrivez mcp.yaml, la route et src/Mcp/TicketTools.php, puis vérifiez avec debug:mcp.
  3. Appelez list_tickets et get_ticket depuis l'Inspector, en ère modern puis legacy.
  4. Rejouez vos requêtes curl d'erreur du chapitre « Le protocole » : comparez les réponses avec celles de tickets-raw.
  5. Branchez le serveur dans VS Code et interrogez-le depuis Copilot.
