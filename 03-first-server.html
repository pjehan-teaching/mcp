Un premier serveur avec Symfony

Objectif

Sans attendre, écrivons un serveur MCP à la main, dans une application Symfony, sans SDK.

  • Le fil rouge : une application de tickets de support (Doctrine + SQLite)
  • Un seul contrôleur, une seule route : POST /mcp
  • Trois méthodes : server/discover, tools/list et tools/call
  • Un seul tool : list_tickets

Un serveur MCP est un simple point d'entrée HTTP qui reçoit et renvoie du JSON.

Le chapitre suivant enrichira ce contrôleur, règle après règle, en découvrant le protocole.

Créer le projet

symfony new tickets-raw
# sans le binaire symfony : composer create-project symfony/skeleton tickets-raw
cd tickets-raw
composer require orm serializer monolog # répondre « n » à la recette Docker
composer require --dev orm-fixtures maker

Une base SQLite suffit : on la déclare dans .env.local, qui surcharge .env :

echo 'DATABASE_URL="sqlite:///%kernel.project_dir%/var/data.db"' > .env.local
  • symfony new : Symfony 8.1, PHP 8.4 ou plus
  • orm : Doctrine ORM ; serializer : transforme les objets en JSON
  • monolog : journalise dans var/log/dev.log, avec le détail des exceptions
  • orm-fixtures : données de départ ; maker : générateurs de code (make:entity…)
Installing Symfony

L'entité Ticket

Un ticket a un titre, une description, un statut (open ou closed) et, éventuellement, un assigné.

php bin/console make:entity Ticket \
    --field=title:string \
    --field=description:text \
    --field=status:string:20 \
    --field='assignee:string?'
  • Syntaxe : nom:type:longueur ; ? rend la propriété nullable
  • L'identifiant id est ajouté automatiquement
  • La commande crée src/Entity/Ticket.php (propriétés privées, getters et setters) et src/Repository/TicketRepository.php

Migrations DoctrineFixturesBundle

Ce que reçoit le serveur

Le client envoie une requête JSON-RPC 2.0 dans le corps d'un POST :

{
  "jsonrpc": "2.0",
  "id": 3,
  "method": "tools/call",
  "params": { "name": "list_tickets", "arguments": { "status": "open" } }
}

Le serveur répond avec le même id et un result :

{
  "jsonrpc": "2.0",
  "id": 3,
  "result": {
    "resultType": "complete",
    "content": [{ "type": "text", "text": "[{\"id\":1,\"title\":\"Connexion impossible\",…}]" }]
  }
}
Base protocol

Trois méthodes suffisent

MéthodeLe client demande…Le serveur renvoie…
server/discoverqui es-tu, que sais-tu faire ?versions supportées, capacités
tools/listquels tools proposes-tu ?nom, description et schéma de chaque tool
tools/callexécute ce tool avec ces argumentsle résultat du tool
  • Le host transmet la liste des tools au modèle
  • Le modèle choisit un tool et ses arguments, le client exécute tools/call
  • capabilities annonce les familles prises en charge (tools, resources…), pas leur contenu : le client obtient la liste des tools avec tools/list
Tools Discovery

McpController : la route

<?php

namespace App\Controller;

use App\Repository\TicketRepository;
use Symfony\Component\HttpFoundation\JsonResponse;
use Symfony\Component\HttpFoundation\Request;
use Symfony\Component\Routing\Attribute\Route;
use Symfony\Component\Serializer\SerializerInterface;

#[Route('/mcp', name: 'mcp', methods: ['POST'])]
final class McpController
{
    public function __construct(
        private readonly TicketRepository $tickets,
        private readonly SerializerInterface $serializer,
    ) {
    }
  • La route n'accepte que POST : un GET reçoit automatiquement 405 Method Not Allowed
  • Le dépôt et le Serializer sont injectés par l'autowiring
  • Pas besoin d'AbstractController : le contrôleur n'utilise aucun de ses raccourcis

McpController : router les méthodes

    public function __invoke(Request $request): JsonResponse
    {
        $message = json_decode($request->getContent(), true);
        $params = $message['params'] ?? [];

        $result = match ($message['method']) {
            'server/discover' => [
                'supportedVersions' => ['2026-07-28'],
                'capabilities' => ['tools' => new \stdClass()],
                'ttlMs' => 3_600_000,
                'cacheScope' => 'public',
            ],
            'tools/list' => ['tools' => [$this->listTicketsTool()], 'ttlMs' => 300_000, 'cacheScope' => 'public'],
            'tools/call' => $this->listTickets($params['arguments'] ?? []),
        };

        return new JsonResponse([
            'jsonrpc' => '2.0',
            'id' => $message['id'],
            'result' => ['resultType' => 'complete', ...$result],
        ]);
    }
  • ttlMs et cacheScope indiquent au client combien de temps il peut garder la réponse : obligatoires pour server/discover et les listes, sans quoi l'Inspector rejette la réponse
  • new \stdClass() produit un objet JSON vide {}, là où [] produirait un tableau
  • new JsonResponse() encode avec json_encode() ; $this->json() passerait par le Serializer, qui transformerait ce {} en []

Pourquoi __invoke() ?

__invoke() est une méthode magique de PHP : elle rend un objet appelable comme une fonction.

$controller($request); // équivaut à $controller->__invoke($request)
  • Quand une route pointe vers une classe, Symfony appelle __invoke()
  • Un serveur MCP n'a qu'un seul point d'entrée : la classe entière est l'action
  • L'attribut #[Route] se place alors sur la classe

Même convention que les listeners, les handlers Messenger ou les commandes invocables : une classe, une responsabilité.

McpController : décrire le tool

Un tool est décrit par un nom, une description et un JSON Schema de ses arguments :

    private function listTicketsTool(): array
    {
        return [
            'name' => 'list_tickets',
            'description' => 'Liste les tickets de support, éventuellement filtrés par statut.',
            'inputSchema' => [
                'type' => 'object',
                'properties' => [
                    'status' => ['type' => 'string', 'enum' => ['open', 'closed']],
                ],
            ],
        ];
    }

Le modèle ne voit que ces informations pour décider d'appeler le tool : la description compte autant que le code.

Tool

McpController : exécuter le tool

    private function listTickets(array $arguments): array
    {
        $status = $arguments['status'] ?? null;
        $tickets = $status ? $this->tickets->findBy(['status' => $status]) : $this->tickets->findAll();

        return ['content' => [[
            'type' => 'text',
            'text' => $this->serializer->serialize($tickets, 'json'),
        ]]];
    }
}
  • Le résultat est une liste de contenus destinés au modèle : ici un seul texte
  • Les tickets sont donc encodés en JSON dans une chaîne de caractères
  • serialize() lit chaque propriété du ticket par son getter

Pour l'instant, tools/call ignore le nom du tool demandé : nous corrigerons cela au chapitre suivant.

Lancer et tester

On lance le serveur web local de Symfony, en HTTP :

symfony serve --no-tls
# sans le binaire symfony : php -S localhost:8000 -t public

Dans un autre terminal, listons les tools :

curl -X POST http://localhost:8000/mcp \
  -H 'Content-Type: application/json' \
  -d '{"jsonrpc": "2.0", "id": 2, "method": "tools/list"}'
{"jsonrpc":"2.0","id":2,"result":{"resultType":"complete","tools":[{"name":"list_tickets",
  "description":"Liste les tickets de support, …","inputSchema":{"type":"object",…}}],
  "ttlMs":300000,"cacheScope":"public"}}

Appeler le tool

curl -X POST http://localhost:8000/mcp \
  -H 'Content-Type: application/json' \
  -d '{"jsonrpc": "2.0", "id": 3, "method": "tools/call",
       "params": {"name": "list_tickets", "arguments": {"status": "open"}}}'

Réponse (mise en forme) :

{
  "jsonrpc": "2.0",
  "id": 3,
  "result": {
    "resultType": "complete",
    "content": [{
      "type": "text",
      "text": "[{\"id\":1,\"title\":\"Connexion impossible\",…,\"status\":\"open\",\"assignee\":null},
               {\"id\":2,\"title\":\"Facture en double\",…,\"status\":\"open\",\"assignee\":\"alice\"}]"
    }]
  }
}

C'est exactement ce que fera un client MCP à la demande du modèle.
