WebMCP

Le problème de l'actuation

Un agent de navigateur (assistant intégré, extension…) accomplit des tâches pour l'utilisateur sur les pages qu'il visite.

  • Sans aide, il fait de l'actuation : il lit le DOM, devine le rôle d'un bouton, simule clics et saisies
  • Chaque étape est sujette à interprétation : lent, fragile, et un redesign suffit à tout casser
  • Avec WebMCP, la page déclare ses tools : un nom, une description, un JSON Schema
  • Le tool s'exécute dans la page, sous les yeux de l'utilisateur

L'agent appelle une fonction au lieu de deviner l'interface.

WebMCP

WebMCP en bref

  • Proposition de standard web, portée par le groupe communautaire Web Machine Learning du W3C
  • Inspirée de MCP : n'en reprend que les tools, sans JSON-RPC, resources ni prompts
  • Deux API :
    • impérative : JavaScript, document.modelContext.registerTool()
    • déclarative : attributs HTML sur un <form>
  • Amélioration progressive : sans agent, la page fonctionne comme avant
  • Les tools n'existent que tant que la page est ouverte

WebMCP versus MCP

Deux technologies complémentaires

  • MCP : la couche de services, disponible pour tout host, à tout moment
  • WebMCP : le dernier kilomètre, quand l'utilisateur a le site ouvert
    • l'agent agit avec la session de l'utilisateur (cookies, état de la page)
    • pas d'aller-retour vers un serveur distant pour découvrir les tools
  • Fil rouge : le serveur MCP tickets sert Copilot ; des tools WebMCP sur les pages de l'application servent l'agent du navigateur
  • Cas d'usage : support client, réservation, formulaires longs, filtres complexes, diagnostic

API impérative : registerTool()

await document.modelContext.registerTool({
  name: 'assign_ticket',
  description: 'Assigne un ticket à un membre du support.',
  inputSchema: {
    type: 'object',
    properties: {
      id: { type: 'integer', description: 'Identifiant du ticket' },
      assignee: { type: 'string', description: 'Nom du membre du support' },
    },
    required: ['id', 'assignee'],
  },
  execute: async ({ id, assignee }) => {
    const response = await fetch(`/tickets/${id}/assign`, {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify({ assignee }),
    });
    if (!response.ok) {
      return `Ticket #${id} introuvable ou non modifiable (HTTP ${response.status}).`;
    }
    document.querySelector(`[data-ticket="${id}"] .assignee`).textContent = assignee;
    return `Ticket #${id} assigné à ${assignee}.`;
  },
});
Imperative API

API impérative : registerTool()

  • name, description et inputSchema : comme un tool MCP
  • execute reçoit les arguments ; la valeur renvoyée est transmise au modèle
  • fetch() part avec les cookies de session : l'agent agit avec les droits de l'utilisateur connecté, sans OAuth
  • Le tool met à jour l'interface : l'utilisateur voit le résultat
  • Les contraintes du schéma ne sont pas garanties : revalider côté serveur et renvoyer une erreur que le modèle peut corriger

React (usewebmcp), Vue (useWebMCP de @vueuse/core) et Angular proposent une intégration expérimentale.

// close_ticket
annotations: { consequentialHint: true }

Les annotations MCP vues au chapitre Tools sont différentes : seul readOnlyHint est commun.

Tool annotations

Retirer un tool, annuler une exécution

const closeTicketTool = {
  name: 'close_ticket',
  // ...
  execute: async ({ id }, { signal }) => {
    const response = await fetch(`/tickets/${id}/close`, { method: 'POST', signal });
    // ...
  },
};

const controller = new AbortController();
await document.modelContext.registerTool(closeTicketTool, { signal: controller.signal });

// Plus tard, quand la page n'affiche plus de ticket ouvert
controller.abort();
  • Un tool s'enregistre quand il est utile dans l'état de la page, et se retire sinon
  • Depuis Chrome 153, retirer un tool n'interrompt pas ses exécutions en cours
  • signal est déclenché quand l'utilisateur ou l'agent annule l'exécution
Unregister tools

Côté agent : découvrir et exécuter

const tools = await document.modelContext.getTools();
const tool = tools.find((t) => t.name === 'assign_ticket');

const result = await document.modelContext.executeTool(tool, { id: 3, assignee: 'alice' });
// 'Ticket #3 assigné à alice.'

document.modelContext.addEventListener('toolchange', () => {
  // La liste des tools a changé : la relire avant le prochain appel au modèle
});
  • L'équivalent de tools/list et tools/call, sans protocole réseau
  • Utilisé par les agents (une extension passe par un content script), et pratique pour tester dans la console
  • executeTool() renvoie null si le tool déclenche une navigation
Discover tools

API déclarative : un formulaire devient un tool

<form action="/tickets" method="get" toolautosubmit
      toolname="search_tickets"
      tooldescription="Recherche des tickets par mot-clé et par statut.">
    <label for="q">Mot-clé</label>
    <input id="q" name="q"
           toolparamdescription="Mot recherché dans le titre et la description">
    <label for="status">Statut</label>
    <select id="status" name="status" required
            toolparamdescription="Statut des tickets recherchés">
        <option value="open">Ouverts</option>
        <option value="closed">Fermés</option>
    </select>
    <button type="submit">Rechercher</button>
</form>
  • Le navigateur met le formulaire au premier plan et le remplit sous les yeux de l'utilisateur
  • Description d'un champ : toolparamdescription, sinon son <label>, sinon aria-description
Declarative API

Le schéma déduit par le navigateur

{
  "name": "search_tickets",
  "description": "Recherche des tickets par mot-clé et par statut.",
  "inputSchema": {
    "type": "object",
    "properties": {
      "q": { "type": "string", "description": "Mot recherché dans le titre et la description" },
      "status": {
        "type": "string",
        "anyOf": [
          { "type": "string", "const": "open", "title": "Ouverts" },
          { "type": "string", "const": "closed", "title": "Fermés" }
        ],
        "enum": ["open", "closed"],
        "description": "Statut des tickets recherchés"
      }
    },
    "required": ["status"]
  }
}

Un champ = une propriété nommée par son attribut name ; un <select> donne une valeur (const) et un libellé (title) par option ; required se retrouve dans required.

Tool parameters

Soumettre le formulaire

  • Sans toolautosubmit : l'agent remplit, l'utilisateur clique lui-même sur le bouton
  • Avec toolautosubmit : l'agent soumet le formulaire, ce qui déclenche la navigation
  • event.agentInvoked : la soumission vient d'un agent
  • event.respondWith(promise), après preventDefault() : la valeur résolue est renvoyée au modèle
form.addEventListener('submit', (event) => {
  if (!event.agentInvoked) {
    return; // soumission classique par l'utilisateur
  }
  event.preventDefault();
  event.respondWith(searchTickets(new FormData(form))); // met à jour la liste, résume le résultat
});

Iframes d'une autre origine

Par défaut, les tools d'une iframe d'une autre origine sont invisibles. Trois conditions pour les partager :

<!-- https://example.com : déléguer la permission tools -->
<iframe src="https://partner.org/widget" allow="tools"></iframe>
// https://partner.org : exposer le tool à une origine choisie
await document.modelContext.registerTool(tool, { exposedTo: ['https://example.com'] });

// https://example.com : demander explicitement les tools de cette origine
const tools = await document.modelContext.getTools({ fromOrigins: ['https://partner.org'] });

N'exposez un tool qu'aux origines à qui vous confieriez ses données ou ses actions.

Cross-origin iframes

Sécurité

  • Toute extension disposant d'un content script peut lister et exécuter les tools de la page
  • Injection de prompt indirecte : un tool qui renvoie du contenu saisi par des utilisateurs porte untrustedContentHint
  • Action irréversible : consequentialHint permet à l'agent ou au navigateur d'exiger une confirmation
  • Les annotations sont des indications de la page : un site malveillant peut mentir
  • Un tool en lecture seule peut révéler des données personnelles
  • Le schéma n'est pas garanti : la validation reste côté serveur
WebMCP tool security Agent security

Bonnes pratiques

  • Un tool, une action : deux tools qui se chevauchent font hésiter l'agent
  • Un nom précis : create_event crée, start_event_creation ouvre le formulaire
  • Une description positive : ce que fait le tool et quand l'utiliser, plutôt que des interdictions
  • Des entrées brutes ("11:00 to 15:00") et des valeurs parlantes (shipping="Express" plutôt que shipping_id=1)
  • Des erreurs qui guident : « Aucun résultat de recherche. Lancez d'abord search_flights. »
  • Mettre l'interface à jour avant de répondre
  • Budgets recommandés : nom 30 caractères, description 500, paramètre 150, résultat 1 500

webmcp-extension

Une extension Chrome open source : un agent d'exemple dans le panneau latéral, pour tester les tools de son site.

  • Liste les tools de la page et de ses iframes, et suit toolchange
  • Envoie un prompt au modèle, exécute les tools qu'il appelle et affiche la réponse en streaming
  • Deux backends :
    • serveur Node.js local : Google, OpenAI, Anthropic ou Ollama via l'AI SDK ; les clés d'API restent sur le serveur
    • modèle embarqué via la Prompt API : ni serveur ni clé, les données restent sur le poste (chrome://flags/#prompt-api-tool-use)
  • Un tableau de bord journalise chaque requête envoyée au modèle

webmcp-extension : les annotations en action

L'extension fait toujours confiance aux annotations, pour montrer leur effet sur un agent :

AnnotationComportement
readOnlyHint: trueLe tool s'exécute sans demander
readOnlyHint: falseL'utilisateur autorise d'abord : une fois, ou pour le site le temps de la conversation
consequentialHint: trueL'utilisateur autorise à chaque fois, même si le tool se dit en lecture seule
untrustedContentHint: trueLe résultat est encodé en Base64 ou entouré d'un marqueur aléatoire (spotlighting), et le modèle est prévenu de ne pas y lire d'instructions

Résultat limité à 8 000 caractères ; au-delà de 10 tours d'appels de tools, l'agent demande s'il doit continuer.

webmcp-types

Les types TypeScript de document.modelContext et des tools :

npm install --save-dev webmcp-types   # puis "types": ["webmcp-types"] dans tsconfig.json
document.modelContext?.registerTool({
  name: 'assign_ticket',
  description: 'Assigne un ticket à un membre du support.',
  inputSchema: {
    type: 'object',
    properties: { id: { type: 'integer' }, assignee: { type: 'string' } },
    required: ['id'],
  },
  execute: async ({ id, assignee }, { signal }) => {
    // id : number, assignee : string | undefined, signal : AbortSignal
    return `Ticket #${id} assigné.`;
  },
});

Les types des arguments de execute() sont déduits de inputSchema : une propriété absente de required devient facultative.

Exercice

Rendez une page web du projet tickets utilisable par un agent de navigateur.

  1. Activez chrome://flags/#enable-webmcp-testing et relancez Chrome.
  2. Avec make:controller, créez une page /tickets qui liste les tickets (un attribut data-ticket par ligne).
  3. Ajoutez le formulaire déclaratif search_tickets, traité en GET par le contrôleur.
  4. Enregistrez en JavaScript un tool get_ticket qui renvoie le détail d'un ticket affiché, avec les annotations adaptées.
  5. Vérifiez dans DevTools (Application → WebMCP) que les deux tools apparaissent, puis exécutez-les à la main.
  6. Avec webmcp-extension, demandez « Montre-moi les tickets ouverts », puis « Résume le ticket 2 ».
  7. Bonus : créez un ticket dont la description contient des instructions, et comparez la réponse avec et sans untrustedContentHint.
