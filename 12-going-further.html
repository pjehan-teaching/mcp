Extension Tasks

Certaines opérations durent des minutes ou des heures : pipeline CI, import massif, validation humaine…

  • Le serveur renvoie un identifiant de tâche au lieu de bloquer la requête
  • Le client interroge l'état avec tasks/get, fournit une entrée avec tasks/update, annule avec tasks/cancel
  • La tâche survit à une déconnexion du client
  • Anciennement expérimentale dans le cœur du protocole, elle devient une extension en 2026-07-28

Tasks : les messages

tools/call renvoie une tâche

{
  "jsonrpc": "2.0",
  "id": 7,
  "result": {
    "resultType": "task",
    "taskId": "task_8f2c1d",
    "status": "working",
    "createdAt": "2026-09-17T10:00:00Z",
    "lastUpdatedAt": "2026-09-17T10:00:00Z",
    "ttlMs": 3600000,
    "pollIntervalMs": 5000
  }
}

Puis le client interroge

{
  "jsonrpc": "2.0",
  "id": 8,
  "method": "tasks/get",
  "params": { "taskId": "task_8f2c1d", "_meta": { … } }
}

Tant que la tâche n'est pas terminée, le client respecte pollIntervalMs. Une fois completed, result contient le résultat du tool.

Extension Skills

Un skill est un dossier contenant un fichier SKILL.md : des instructions de workflow et des fichiers d'appui (format Agent Skills).

  • Découverte avec skills/list et skills/get
  • Fichiers lus avec resources/read
  • Le host décide quand charger un skill dans le contexte du modèle, souvent avec l'accord de l'utilisateur
"capabilities": {
  "resources": {},
  "extensions": {
    "io.modelcontextprotocol/skills": { "directoryRead": true }
  }
}

MCP Registry

  • Registre officiel des métadonnées des serveurs MCP publics (en préversion)
  • Chaque serveur est décrit par un server.json : nom, paquet ou URL distante, configuration
  • Noms en DNS inversé, vérifiés : io.github.utilisateur/serveur
  • Destiné aux agrégateurs et places de marché, pas directement aux hosts

  "version": "1.0.0",
  "remotes": [

  ]

Construire un client

<?php

require __DIR__ . '/vendor/autoload.php';

use Mcp\Client;
use Mcp\Client\Transport\StdioTransport;

$client = Client::builder()
    ->setClientInfo('tickets-cli', '1.0.0')
    ->build();

$client->connect(new StdioTransport(command: 'php', args: [__DIR__ . '/server.php']));

foreach ($client->listTools()->tools as $tool) {
    echo "- {$tool->name} : {$tool->description}\n";
}

$result = $client->callTool('get_ticket', ['id' => 2]);
echo $result->content[0]->text, "\n";

$client->disconnect();

Construire un host

Un client seul ne suffit pas : le host fait le lien entre les serveurs et le modèle.

  1. Récupérer les tools de chaque serveur avec tools/list
  2. Les transmettre au modèle via l'API de son fournisseur (tool use / function calling)
  3. Quand le modèle demande un appel, le faire valider par l'utilisateur si nécessaire
  4. Exécuter tools/call sur le bon serveur et renvoyer le résultat au modèle
  5. Répéter jusqu'à la réponse finale

C'est ce que font VS Code, Claude ou ChatGPT, avec en plus la gestion des resources, des prompts et de l'elicitation.

Bonus : un vrai serveur d'autorisation

Protégez le fil rouge avec OAuth en vous appuyant sur l'exemple oauth-keycloak du SDK PHP :

  1. Lancez Keycloak avec Docker et importez le realm fourni.
  2. Publiez les métadonnées RFC 9728 avec ProtectedResourceMetadataMiddleware.
  3. Validez les jetons avec AuthorizationMiddleware et JwtTokenValidator (émetteur, audience).
  4. Réservez close_ticket et assign_ticket à un scope d'écriture.
  5. Connectez-vous depuis l'Inspector et observez le flux d'autorisation.
