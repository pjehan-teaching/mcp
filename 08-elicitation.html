MRTR et elicitation

Demander une information en cours de route

Certains traitements ne peuvent pas aboutir sans l'utilisateur :

  • confirmer une action destructrice : fermer un ticket, supprimer des données
  • compléter une information manquante : la priorité d'un nouveau ticket
  • faire un choix : plusieurs clients portent le même nom

L'elicitation permet au serveur de formuler une demande que le client présente à l'utilisateur, avant de reprendre le traitement.

Elicitation

Ère legacy : le serveur interroge le client

Client                                     Serveur
│ tools/call close_ticket (id 1)              │
│────────────────────────────────────────────►│
│                                             │  traitement en cours…
│ elicitation/create (id 7)                   │
│◄────────────────────────────────────────────│
│                                             │  le serveur attend la réponse
│ réponse (id 7) : action accept              │
│────────────────────────────────────────────►│
│ résultat (id 1)                             │
│◄────────────────────────────────────────────│
  • Le serveur envoie sa propre requête pendant le traitement de tools/call
  • La requête d'origine reste ouverte jusqu'à la réponse de l'utilisateur
  • Le serveur doit garder l'état du traitement en mémoire, sur la même instance

Ère modern : Multi Round-Trip Requests

Client                                     Serveur
│ tools/call close_ticket (id 2)              │
│────────────────────────────────────────────►│
│                                             │  il manque une confirmation
│ résultat (id 2) : input_required            │
│◄────────────────────────────────────────────│
│                                             │  le serveur ne garde rien en mémoire
│ tools/call (id 3) + inputResponses          │
│────────────────────────────────────────────►│
│ résultat (id 3) : complete                  │
│◄────────────────────────────────────────────│
  • Le serveur répond qu'il lui manque une information (input_required)
  • Le client recueille la réponse, puis relance la requête d'origine avec un nouvel id
  • Aucune requête ne reste ouverte : n'importe quelle instance peut traiter la relance

MRTR : la relance

Le client relance la même requête, complétée par inputResponses :

{"jsonrpc": "2.0", "id": 3, "method": "tools/call", "params": {
  "name": "close_ticket", "arguments": {"id": 2},
  "inputResponses": {
    "elicitation_1": {"action": "accept", "content": {"confirm": true}}
  },
  "_meta": {…}}}

Le serveur termine le traitement :

{"jsonrpc": "2.0", "id": 3, "result": {
  "resultType": "complete",
  "content": [{"type": "text", "text": "Ticket #2 fermé."}],
  "isError": false
}}

inputResponses reprend les clés de inputRequests (elicitation_1).

Multi Round-Trip Requests

requestState

Quand le traitement nécessite plusieurs allers-retours, le serveur peut joindre un requestState à input_required :

  • une chaîne opaque, que le client renvoie telle quelle lors de la relance
  • elle transporte ce que le serveur veut retrouver : réponses précédentes, étape atteinte…
  • elle passe par le client : elle doit être signée, et elle n'est pas chiffrée

Le SDK PHP la signe avec une clé HMAC, à configurer dès qu'un tool pose plusieurs questions :

->setRequestState($_ENV['MCP_REQUEST_STATE_KEY'], ttl: 600)

Elicitation : deux modes

Mode formMode url
PrincipeLe client affiche un formulaireLe client ouvre une URL externe
DonnéesTransitent par le clientNe transitent pas par le client
UsageConfirmation, choix, informations simplesMots de passe, clés d'API, paiement, consentement OAuth

Un serveur ne doit jamais demander de secret en mode form.

L'utilisateur répond par accept (avec un contenu), decline ou cancel.

Requested schema

Elicitation avec le SDK

    /**
     * Ferme un ticket résolu, après confirmation de l'utilisateur.
     */
    #[McpTool(name: 'close_ticket', annotations: new ToolAnnotations(destructiveHint: true))]
    public function close(RequestContext $context, int $id): string
    {
        $ticket = $this->get($id);

        $answer = $context->getClientGateway()->elicit(
            "Fermer le ticket #$id « {$ticket['title']} » ?",
            new ElicitationSchema(
                ['confirm' => new BooleanSchemaDefinition(title: 'Confirmer la fermeture')],
                required: ['confirm'],
            ),
        );

        if (!$answer->isAccepted() || !$answer->content['confirm']) {
            return "Fermeture du ticket #$id annulée par l'utilisateur.";
        }

        $this->tickets->close($id);
        return "Ticket #$id fermé.";
    }
}

Un code identique pour les deux ères

elicit() fonctionne quelle que soit l'ère du client :

  • ère modern : le SDK renvoie input_required, puis réexécute la méthode depuis le début lors de la relance, avec la réponse
  • ère legacy (VS Code aujourd'hui) : le SDK envoie une vraie requête elicitation/create et attend la réponse

Une méthode qui pose une question peut être exécutée plusieurs fois : placez les effets de bord après la dernière question.

Ici, get() ne fait que lire : seul close() modifie la base, après la confirmation.

SDK : Asking for input

Capacités du client

  • Un client qui accepte l'elicitation le déclare dans clientCapabilities : {"elicitation": {"form": {}, "url": {}}}
  • Un objet vide {"elicitation": {}} équivaut au seul mode form
  • Le serveur ne doit pas demander ce que le client ne sait pas fournir : le SDK répond alors par l'erreur -32021
  • Pour proposer une solution de repli, testez $context->getClientGateway()->supportsElicitation()
