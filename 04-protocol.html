Le protocole

Notre contrôleur est trop naïf

Le serveur du chapitre précédent fonctionne avec curl, mais il ignore presque tout du protocole :

  • il ne vérifie pas la version du protocole demandée par le client
  • une méthode inconnue provoque une erreur 500
  • tools/call exécute list_tickets quel que soit le nom demandé
  • il ignore les en-têtes HTTP imposés par le transport
  • il n'indique pas son identité (serverInfo)

Dans ce chapitre, chaque règle du protocole devient quelques lignes de code dans McpController.

JSON-RPC 2.0

Tous les messages MCP suivent la spécification JSON-RPC 2.0 : un format d'appel de procédure à distance encodé en JSON.

MessageChampsRéponse attendue
Requêtejsonrpc, id, method, paramsoui, avec le même id
Réponsejsonrpc, id, result ou error—
Notificationjsonrpc, method, params (pas d'id)non
  • L'id est une chaîne ou un entier, jamais null
  • Un même émetteur ne réutilise pas un id encore en attente de réponse

Base protocol

Un protocole sans état (Stateless)

Depuis 2026-07-28, MCP est sans état : toute l'information nécessaire au traitement d'une requête est dans la requête elle-même.

  • Pas de poignée de main à l'ouverture, pas de session
  • Le serveur ne déduit rien des requêtes précédentes, même sur la même connexion
  • N'importe quelle instance du serveur peut traiter n'importe quelle requête
  • Un état qui dure entre plusieurs requêtes passe par un identifiant explicite, par exemple un argument de tool

C'est le modèle d'exécution de PHP : chaque requête HTTP est traitée indépendamment. Un contrôleur Symfony suffit.

Statelessness

Pourquoi MCP n'a pas toujours été sans état ?

  • MCP a été conçu pour un usage local, en s'inspirant du Language Server Protocol (LSP) qui relie les éditeurs aux analyseurs de code
  • Le client lançait le serveur comme sous-processus et dialoguait avec lui en stdio pendant toute sa durée de vie : une poignée de main initiale était naturelle
  • Le serveur devait aussi pouvoir solliciter le client à tout moment (sampling, elicitation, roots) : il fallait une connexion vivante et une session

Une fois MCP déployé comme service web distant, les sessions sont devenues un frein : sticky sessions derrière un répartiteur de charge, serverless difficile, montée en charge compliquée.

La version 2026-07-28 se rapproche donc du modèle HTTP classique.

Key changes

Les métadonnées _meta

Chaque requête transporte sa version et les capacités du client dans params._meta :

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/call",
  "params": {
    "name": "list_tickets",
    "arguments": { "status": "open" },
    "_meta": {
      "io.modelcontextprotocol/protocolVersion": "2026-07-28",
      "io.modelcontextprotocol/clientCapabilities": { "elicitation": {} },
      "io.modelcontextprotocol/clientInfo": { "name": "example-client", "version": "1.0.0" }
    }
  }
}

protocolVersion et clientCapabilities sont obligatoires, clientInfo est recommandé.

_meta

Lire la requête

On extrait une fois pour toutes ce dont les vérifications auront besoin :

final class McpController
{
    private const VERSION = '2026-07-28';
    private const SERVER_INFO = ['name' => 'tickets', 'version' => '1.0.0'];

    public function __construct(
        private readonly TicketRepository $tickets,
        private readonly SerializerInterface $serializer,
    ) {
    }

    public function __invoke(Request $request): JsonResponse
    {
        $message = json_decode($request->getContent(), true) ?? [];
        $id = $message['id'] ?? null;
        $method = $message['method'] ?? null;
        $params = $message['params'] ?? [];
        $version = $params['_meta']['io.modelcontextprotocol/protocolVersion'] ?? null;
        $name = $method === 'tools/call' ? ($params['name'] ?? null) : null;

?? null évite les erreurs sur une requête mal formée : les vérifications suivantes la rejetteront.

Vérifier la version

Sans poignée de main, la version est vérifiée à chaque requête. Une version non supportée renvoie 400 et l'erreur -32022, avec la liste des versions acceptées :

        if ($version !== self::VERSION) {
            return $this->error($id, -32022, 'Unsupported protocol version', 400, [
                'supported' => [self::VERSION],
                'requested' => $version,
            ]);
        }

Le client choisit alors une version de la liste supported et renvoie sa requête.

Versioning

Le résultat et resultType

{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "resultType": "complete",
    "content": [{ "type": "text", "text": "[{\"id\": 1, \"title\": \"Connexion impossible\", …}]" }],
    "_meta": {
      "io.modelcontextprotocol/serverInfo": { "name": "tickets", "version": "1.0.0" }
    }
  }
}
  • resultType est obligatoire : "complete" pour un résultat final, "input_required" quand le serveur attend une information (voir le chapitre MRTR)
  • Un client traite un resultType absent comme "complete" (serveurs plus anciens)
  • Le serveur s'identifie dans le _meta de chaque résultat avec serverInfo
ResultType

Renvoyer le résultat

        return new JsonResponse(['jsonrpc' => '2.0', 'id' => $id, 'result' => [
            'resultType' => 'complete',
            ...$result,
            '_meta' => ['io.modelcontextprotocol/serverInfo' => self::SERVER_INFO],

L'opérateur ... déplie le tableau associatif $result préparé par le match.

Error codes

Renvoyer une erreur

Une méthode privée construit toutes les réponses en erreur :

    private function error(mixed $id, int $code, string $message, int $status = 200, array $data = []): JsonResponse
    {
        $error = ['code' => $code, 'message' => $message, ...($data ? ['data' => $data] : [])];

        return new JsonResponse(['jsonrpc' => '2.0', 'id' => $id, 'error' => $error], $status);
    }
  • Le code JSON-RPC explique l'erreur au client
  • Le code HTTP renseigne aussi les intermédiaires (proxy, répartiteur de charge…) qui ne lisent pas le corps

Méthode ou tool inconnu

        if ($method === 'tools/call' && $name !== 'list_tickets') {
            return $this->error($id, -32602, "Unknown tool: $name");
        }

        $result = match ($method) {
            'server/discover' => [
                'supportedVersions' => [self::VERSION],
                'capabilities' => ['tools' => new \stdClass()],
                'ttlMs' => 3_600_000,
                'cacheScope' => 'public',
            ],
            'tools/list' => ['tools' => [$this->listTicketsTool()], 'ttlMs' => 300_000, 'cacheScope' => 'public'],
            'tools/call' => $this->listTickets($params['arguments'] ?? []),
            default => null,
        };

        if ($result === null) {
            return $this->error($id, -32601, 'Method not found', 404);
        }
  • Méthode non implémentée : 404 Not Found et -32601
  • Tool inconnu : erreur de protocole -32602

Discovery

Mettre en cache

Sans session, c'est le client qui garde les réponses en cache. Le serveur doit lui indiquer pour combien de temps : nous l'avons déjà fait au chapitre précédent, car l'Inspector rejette une réponse sans ces champs.

  • ttlMs : durée de validité en millisecondes (0 : toujours périmée)
  • cacheScope : public (identique pour tous) ou private (propre à l'utilisateur)
Méthodes concernéesDans notre contrôleur
server/discover1 heure, public
tools/list, prompts/list, resources/list…5 minutes, public
resources/read—

tools/call n'est jamais mis en cache.

Caching

Transport stdio

  • Le client lance le serveur comme sous-processus
  • Le serveur lit les messages sur stdin et écrit ses messages sur stdout
  • Un message JSON par ligne, sans retour à la ligne à l'intérieur
  • Les logs vont sur stderr
{"jsonrpc":"2.0","id":1,"method":"tools/list","params":{"_meta":{…}}}
{"jsonrpc":"2.0","id":1,"result":{"resultType":"complete","tools":[…],"ttlMs":0,"cacheScope":"private"}}

Un simple echo ou dump() dans un serveur stdio corrompt le flux de messages.

stdio

Transport Streamable HTTP

C'est le transport de notre contrôleur :

  • Le serveur expose une seule URL (l'endpoint MCP), qui accepte POST
  • Chaque message du client est une requête POST distincte
  • Le serveur répond en application/json, ou en text/event-stream (SSE) pour envoyer des notifications de progression avant la réponse finale
  • Une notification reçue est acquittée par 202 Accepted, sans corps
  • Une méthode inconnue renvoie 404 et l'erreur -32601
Streamable HTTP

Streamable HTTP : les en-têtes

Des champs du corps sont recopiés en en-têtes pour que les intermédiaires routent sans lire le JSON :

POST /mcp HTTP/1.1
Host: localhost:8000
Content-Type: application/json
Accept: application/json, text/event-stream
MCP-Protocol-Version: 2026-07-28
Mcp-Method: tools/call
Mcp-Name: list_tickets

{"jsonrpc": "2.0", "id": 1, "method": "tools/call", "params": {"name": "list_tickets", …}}

MCP-Protocol-Version et Mcp-Method accompagnent toutes les requêtes ; Mcp-Name accompagne tools/call, resources/read et prompts/get.

Request metadata

Vérifier les en-têtes

Un en-tête absent ou en désaccord avec le corps renvoie 400 et l'erreur -32020 :

        if ($request->headers->get('MCP-Protocol-Version') !== $version
            || $request->headers->get('Mcp-Method') !== $method
            || $request->headers->get('Mcp-Name') !== $name) {
            return $this->error($id, -32020, 'Header mismatch', 400);
        }

Un répartiteur de charge qui route sur l'en-tête et un serveur qui exécute le corps doivent parler de la même requête.

Simplification : la spécification prévoit aussi un encodage Base64 de Mcp-Name pour les noms non ASCII.

Server validation

Streamable HTTP : sécurité

  • Le serveur doit valider l'en-tête Origin et répondre 403 s'il est invalide, pour bloquer les attaques par DNS rebinding
  • En local, le serveur écoute uniquement sur localhost
  • Un serveur distant met en place une authentification (voir le chapitre Sécurité)

Sans ces protections, un site web malveillant peut piloter un serveur MCP local depuis le navigateur de l'utilisateur.

Notre contrôleur ne valide pas encore Origin : ce sera le bonus du chapitre suivant.

Un vrai client : l'Inspector

Le MCP Inspector se connecte à notre serveur en ère modern grâce à un fichier de configuration :

{

Sans --cli, l'Inspector ouvre son interface web et affiche l'historique des messages.

Par défaut, l'Inspector utilise l'ère legacy et commencerait par initialize, que notre serveur ne connaît pas.

Inspector CLI

Avant / après : l'ère legacy

Avant 2026-07-28, client et serveur ouvraient une session :

→ initialize                { protocolVersion, capabilities, clientInfo }
← résultat                  { protocolVersion, capabilities, serverInfo }  + Mcp-Session-Id
→ notifications/initialized
→ tools/call   (id 1)       { name: "list_tickets", arguments: { } }       + Mcp-Session-Id
← résultat     (id 1)       { content: [ … ] }

Depuis 2026-07-28, chaque requête est autonome :

→ tools/call   (id 1)       { name: "list_tickets", arguments: { },
                              _meta: { protocolVersion, clientCapabilities } }
← résultat     (id 1)       { resultType: "complete", content: [ … ] }

Ce qu'expose un serveur ne change pas d'une ère à l'autre ; seul le cycle de vie des échanges diffère.

Key changes

Ce qui a disparu

  • Supprimés : initialize, ping, logging/setLevel, resources/subscribe
  • Dépréciés (encore fonctionnels, à ne plus utiliser) : Roots, Sampling et Logging
  • Déplacé dans une extension officielle : Tasks

En septembre 2026, beaucoup de hosts parlent encore l'ère legacy, VS Code compris : notre contrôleur, qui ne parle que l'ère modern, ne peut pas encore y être branché.

Le SDK officiel sert les deux ères avec le même code (chapitre « Le SDK »).
